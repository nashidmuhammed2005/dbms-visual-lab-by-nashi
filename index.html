Understand the components

Three layers of a typical web application

Each layer has a clear responsibility, and the response travels back toward the client.

💻

Client

The browser or app the user interacts with. It sends a request and displays the response.

⚙️

Application server

Runs application logic, validates input, checks permissions, and asks the database for the required information.

🗄️

Database server

Stores organised data, executes queries, and returns matching records to the application server.

Two-tier architecture

Client⟷Server / database

The client communicates directly with the server or database service. This can be simple, but direct database access can create security and maintenance challenges.

Three-tier architecture

Client⟷Application⟷Database

The application layer separates the user interface from business logic and data management. This is common in web applications.

Advantages

Centralised management, shared services, easier updates, and support for many clients.

Limitations

Server or network failures can affect users. Heavy traffic can cause slowdowns, so security, backups, and capacity planning matter.

Examples

College portals, online banking, shopping websites, email, and social media.

Who does the work?

Coordinator vs. workers

Think of the coordinator as the organiser and the workers as the processing units. They are software components, not people.

🧭

Coordinator

Plans or coordinates query execution, assigns portions of work, tracks progress, and combines partial results when needed. Depending on the database, it may be a process or part of a query engine.

⚡

Workers

Execution units that process assigned parts of a query. A worker may be a process, thread, or task running on a CPU core or a separate node.

🧠

Not the same as a CPU core

A CPU core is hardware. A worker is software work being executed. Workers use CPU time, but one worker is not necessarily one dedicated core.

Remember: This animation is only an example, not a real speed test. Adding more workers does not always make a query faster. Workers may need to wait for data, share information, or wait for the coordinator.
Architecture patterns

Three ways to organise processing resources

The key difference is what processors share: memory, disks, or neither.

Processors share main memory and disks. Communication can be fast, but shared resources may become bottlenecks.

Common shared storage

Each node has private memory, but nodes access shared disks. Storage contention and coordination can limit performance.

Shared nothing

Node ACPU · RAM · Disk
Node BCPU · RAM · Disk
Node CCPU · RAM · Disk
Network between nodes

Each node owns its processor, memory, and storage. It can scale well, but data distribution and network communication matter.

Data partitioning

How can a database divide rows?

Range partitioning

Rows are grouped by ranges, such as dates or numeric IDs.

Hash partitioning

A hash function determines which partition receives each row.

Round-robin partitioning

Rows are distributed in turn across the available partitions.

Good partitioning balances work and reduces data movement. Parallel databases are useful for analytics, reporting, data warehousing, retail trends, and large banking workloads.

Why it helps

Suitable large queries can finish faster, and the system can handle large datasets and high workloads.

What can go wrong?

Uneven partitions leave some workers waiting. Data movement, coordination, and failures also add complexity.

Key idea

Divide the work sensibly, keep workers balanced, and combine partial results correctly.
